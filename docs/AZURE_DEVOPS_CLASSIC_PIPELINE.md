# Azure DevOps Classic pipelines: CI/CD scans

How to scan from an Azure DevOps **Classic** (visual designer) build pipeline and have the result
show up in the portal with its build number and a link back to the run.

## YAML vs Classic

Azure DevOps has two pipeline authoring modes:

- **YAML pipelines** keep the pipeline in `azure-pipelines.yml` in the repo. The portal's existing
  Azure Pipelines snippet targets these.
- **Classic pipelines** are built in the web UI as a list of tasks with no file in the repo. You
  cannot paste a YAML snippet into one; you add a **Bash** task and paste a script into it.

Both report as `ci_provider="azure_pipelines"` in the portal. The scan is always `scan_type="cicd"`,
`triggered_by="ci"`.

## Variables

Only the token is required. Define it on the pipeline (Pipeline > Variables) or in a linked
variable group:

| Variable | Notes |
| --- | --- |
| `ZEROSTRIKE_TOKEN` | **Required.** Project API key from the portal. Mark it **secret**. Secret variables are not exported to scripts automatically, so map it explicitly into the Bash task's **Environment Variables** section (`ZEROSTRIKE_TOKEN` = `$(ZEROSTRIKE_TOKEN)`). |
| `ZEROSTRIKE_VERSION` | Optional. Scanner version, default `latest`. Set a release such as `v0.40.0` to pin. |
| `ZEROSTRIKE_FAIL_ON` | Optional. `none`, `critical` or `high`; overrides the default baked into the inline script (the project's CI gate setting when the snippet was copied). |
| `ZEROSTRIKE_PORTAL_URL` | Optional. Portal origin, overrides the one baked into the inline script. |

Non-secret pipeline variables reach the script as environment variables automatically, which is
why the optional ones override the inline defaults without editing the task.

## Task placement and agent

- Add one **Bash** task, type **Inline**, after checkout and build and **before** any deploy task,
  so a failing scan can stop a release.
- Working directory: `$(Build.SourcesDirectory)`.
- Agent: Microsoft-hosted `ubuntu-latest`.
- **Supported platform: Linux amd64 only.** Windows agents and PowerShell are not supported in this
  phase.

## Inline script vs hosted script

Azure DevOps caps a Bash task's inline script at **5000 characters**, and the full scan logic is
longer than that. So the inline script the portal hands out is five lines: it exports
`ZEROSTRIKE_PORTAL_URL` and `ZEROSTRIKE_FAIL_ON` defaults, downloads the full script from
`$ZEROSTRIKE_PORTAL_URL/api/v1/downloads/ci/azure-classic.sh` (public, no token, like the binaries)
and runs it with `bash`. `set -e` makes a failed download fail the task instead of passing silently.

The hosted script is `backend/app/ci_scripts/azure-classic.sh`; the inline one is generated by
`frontend/lib/cicd/azure-classic.ts`. Because the logic is served by the portal, a fix to the
script reaches every Classic pipeline on its next run without anyone re-pasting the task. The
trust boundary is unchanged: the pipeline already runs a binary downloaded from the same portal.

`backend/tests/test_azure_classic_script.py` runs the inline script the way the Bash task does
(written to a file, `bash --noprofile --norc`, the agent's predefined variables as environment
variables) against a stub portal and a stub scanner, covering registration, upload, every gate
value, a pipeline-variable override, and the token failures.

## What the hosted script does

1. Resolve `ZEROSTRIKE_VERSION` (default `latest`) to a concrete release via
   `/api/v1/downloads/zerostrike/<version>/linux-amd64/info`, then use that release for both the
   binary and its checksum, so a release published mid-run cannot mismatch them.
2. Download the scanner for `linux-amd64` and verify its SHA-256 against that release's
   `checksums.txt`. A mismatch aborts.
3. Register the scan: `POST /api/v1/scans` with the API key, sending `triggered_by="ci"`,
   `ci_provider="azure_pipelines"`, the resolved `scanner_version` and the build metadata
   (`ci_build_id` from `Build.BuildId`, `ci_build_number` from `Build.BuildNumber`, `ci_build_url`
   the build results link), plus branch and commit.
4. Run a local scan of `$(Build.SourcesDirectory)` with `--format json`. The report stays on the
   agent until the upload.
5. Upload the JSON report: `POST /api/v1/scans/{id}/upload/json`. This is what marks the scan
   `completed` and ingests findings.
6. Gate. Scanner exit `0` (clean) and `1` (findings) both count as a successful scan; anything
   higher is a real failure.

## The gate: `ZEROSTRIKE_FAIL_ON`

| Value | Critical finding | High finding (no critical) | Medium / low only |
| --- | --- | --- | --- |
| `none` | Warn | Warn | Pass |
| `critical` | **Fail** | Warn | Pass |
| `high` | **Fail** | **Fail** | Pass |

Warn means a red error in the run's issue list and a *partially succeeded* result
(`SucceededWithIssues`); the build does not fail. Task exit codes: `0` passed, `1` findings
tripped the gate, `2` setup failure (token, download, upload). Any other value of
`ZEROSTRIKE_FAIL_ON` behaves as `none`. The same table applies to the YAML snippets.

Request contract for step 3 (all `ci_*` fields optional, enforced server-side in
`backend/app/schemas/scan.py: ScannerCreateScanRequest`):

- `triggered_by` is `"cli"` or `"ci"`. Portal-originated values (`cloud`, `manual`, `sync`) are
  rejected with 422. Omitting it means `cli`, so older scanners keep working.
- Any `ci_*` field requires `triggered_by="ci"`, and `triggered_by="ci"` requires `ci_provider`.
- `ci_build_id` max 64 characters of `[A-Za-z0-9._-]`; `ci_build_number` max 128, no control
  characters; `ci_build_url` max 2048, `http`/`https` with a host, no embedded credentials.
- Empty strings are treated as absent, so an unresolved pipeline variable does not fail the scan.

## Pinned vs latest

The default is `latest`, so a newly published scanner is picked up on the next run with no
pipeline change. The script resolves `latest` once and then downloads that exact release and its
checksum, which avoids the old quirk where `latest/checksums.txt` (newest across **all** platforms)
could disagree with `latest/linux-amd64`. Pin `ZEROSTRIKE_VERSION` to a release when you need
every run to scan with the same engine; a pinned version is immutable once published
(re-uploading different bytes is a 409).

## Branches and pull requests

Run the task in the pipeline triggered by the branch you want tracked (for example `main`), and in
a PR validation pipeline if you want findings before merge. The branch and commit sent with the
scan are what the portal groups history by, so keep one pipeline per branch of interest rather
than one pipeline that scans arbitrary refs.

## Publishing the binary (portal admin)

The download is served from the portal's own storage, which starts empty. Until a portal admin
publishes `linux/amd64` for the version you pin, the download returns 404.

**Temporary manual publish** (placeholder values; uses an admin login, never commit these):

```
curl -fsS -X POST "$PORTAL/api/v1/admin/downloads/zerostrike" \
  -H "Authorization: Bearer $ADMIN_ACCESS_TOKEN" \
  -F version=v0.40.0 -F os=linux -F arch=amd64 \
  -F file=@./zerostrike_linux_amd64
```

**Permanent fix: release automation.** The scanner repo's `.github/workflows/release.yml` publishes
every platform on a tagged release. It needs two repository secrets holding a portal admin
login: `ZS_PORTAL_ADMIN_EMAIL` and `ZS_PORTAL_ADMIN_PASSWORD`. See
[`CICD_SCAN_BINARY_404.md`](./CICD_SCAN_BINARY_404.md) for the full history.

**Check availability** (public, returns metadata only: version, os, arch, filename, sha256,
size_bytes, uploaded_at):

```
curl -f $PORTAL/api/v1/downloads/zerostrike/<version>/linux-amd64/info
```

Whether `linux/amd64` is actually published in production is **not verified from this repo**; run
the check above against the real portal.

## Troubleshooting

- **404 on the binary download (or `/info`).** The message names the platform and version and says
  a portal admin must publish it. Publish it as above, or pin a version that exists.
- **Task fails at the `curl` line of the inline script.** The hosted script could not be fetched:
  check `ZEROSTRIKE_PORTAL_URL` and that the agent can reach the portal.
- **401 when registering the scan.** The API key is invalid, expired or revoked. Create a new key
  in the portal and update `ZEROSTRIKE_TOKEN`.
- **`ZEROSTRIKE_TOKEN` empty in the script.** Secret variables are not auto-exported. Map it in the
  Bash task's Environment Variables as `$(ZEROSTRIKE_TOKEN)`.
- **Upload fails after the local scan succeeded.** The scan is registered but stays `pending`; the
  JSON report remains on the agent for that run only. Re-run the pipeline, or publish the report
  file as a build artifact in an earlier task if you need to keep it.
- **Build fails because of findings.** That is `ZEROSTRIKE_FAIL_ON` doing its job. Raise the
  threshold or set it to `none` to report without gating. Exit code `2` is a scanner failure, not a
  findings result.
- **400 `invalid os-arch`.** Only `linux`, `windows`, `darwin` with `amd64`, `arm64` are valid
  segments; this setup uses `linux-amd64`.
